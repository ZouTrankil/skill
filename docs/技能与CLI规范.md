# 技能与 CLI 规范

本规范约束本仓库后续新增或修改的技能、独立 CLI 和 CLI 包装，目标是让人和 Agent 都能找到入口、理解边界并验证实际行为。项目内更具体的约定和用户明确要求优先。第三方源码、插件及已有工具保留原有接口；不因本规范批量改造，维护时记录差异并按需接入。

## 共通规则

- 新增前先查现有技能、CLI、真实调用方和上游能力，复用已有入口；按职责决定是否需要两者，不为每个技能强制创建 CLI，也不为简单命令增加重复包装。
- 同一能力的源码只确定一处维护位置。记录来源、本地改动、依赖、版本、适用范围与实际验证状态；安装、认证、定时任务和运行环境分别核实，不把收录当作可用。
- 跨机器路径使用仓库相对路径、环境变量或明确的安装方式，不把某台机器的绝对路径写成通用入口。本机实际入口只记在账本中，并注明核验时间。
- 不提交凭据和个人配置；外部请求、写文件、删除、发布等副作用在能力描述和使用说明中写清，由具体任务授权决定是否执行。
- 文档以稳定入口、使用方法、边界和验收为主；过程记录和临时产物放项目约定的位置。上游或接口升级后同步更新能力描述、关联技能和索引。

## 技能

### 位置与内容

- 本仓库维护的全局通用技能放 `.agents/skills/<技能名>/SKILL.md`；项目类共用技能放 `library/project-types/<项目类别>/<技能名>/SKILL.md`；项目专用技能由对应项目维护。名称使用小写字母、数字和连字符，目录名与 `name` 一致。
- `SKILL.md` 包含 YAML frontmatter 的 `name`、`description`，正文写清用途、触发与不适用边界、关键步骤、依赖和失败处理；只添加真实需要的 `scripts/`、`references/` 或 `assets/`。保留已有项目语言和第三方技能的上游信息。
- 只在显式要求时调用的技能，说明触发条件并按客户端支持的配置限制自动调用。不要将自动发现当作运行授权。
- 技能依赖 CLI 时，写明如何找到可执行入口、依赖和替代方式，链接 CLI 账本及能力发现方式；不能假设技能可见即 CLI 已安装。复制技能到其他项目时，不假设原仓库仍存在。

### 登记与验证

- 更新 [README 技能索引](../README.md#技能索引)和 [技能账本](../技能账本.md)：分别说明用途与来源、源码位置、本机发现入口及安装状态。是否设置用户级链接按任务授权和现有同名入口决定，避免覆盖或重复安装。
- 校验 frontmatter、名称和链接；使用脚本的技能还需运行相关脚本。用代表性场景验证触发、关键行为和失败边界，报告静态检查、样本验证与真实环境验证各自的范围。

## 独立 CLI 与包装

### 入口和依赖

- 本仓库维护的独立 CLI 或有实际用途的第三方包装放 `cli/<工具名>/`，提供明确可执行入口。已有上游完整源码或原生入口时沿用其结构，不再复制一套 runner。技能内部辅助脚本继续放技能目录，不因是脚本就升级为独立 CLI。
- 在 [CLI 账本](../CLI账本.md)记录用途、上游与维护归属、源码或调用入口、安装方法、关联技能、本机状态和核验日期。README 提供可发现入口；账本不包含凭据。
- 包装应透传上游参数、标准输入输出和退出状态；日志或错误信息写标准错误，不能污染要求机器读取的标准输出。文件路径和特殊字符按参数传递，不能将输入拼成 shell 命令。
- 写明系统要求、依赖与安装方式、首次运行可能联网或下载，以及离线和依赖缺失时的行为。包装固定上游版本时，记录并同步更新能力描述；升级需重新验证关键路径。CLI 的存在不代表全局 PATH 已配置。
- 能力、参数和输出以实际版本为准。原生 CLI 的 `--help` / `--version` 应可用；包装保留上游的帮助、版本、错误和退出语义。不要覆盖上游已有子命令或标志；如有冲突，保留原接口并记录替代发现入口。

### 能力发现 JSON

对本仓库新建、面向 Agent 调用的独立 CLI 或包装，提供机器可读能力描述。优先复用原生能力发现机制；无原生接口且命令不冲突时，提供 `tool schema` 和 `--output json tool schema`。已有 CLI 或第三方上游保持兼容，其差异在账本说明；Unity CLI 沿用自身的 `tool schema` 协议。

新增包装的 `tool schema` 约定如下，当前可参考 [ast-grep 描述](../cli/ast-grep/capabilities.json)和 [MarkItDown 描述](../cli/markitdown/capabilities.json)：

- 标准输出只包含一个有效 JSON 对象，顶层包括 `command`、`success`、`data`、`errors`、`warnings`；失败须返回非零退出码，错误输出不能伪装成成功。
- `data` 标明工具名、包或来源、对应版本、描述来源、覆盖范围、调用方式和 `tools`。静态清单明确说明是否只列常用能力，不宣称是上游完整能力，也不因 schema 可读就声称运行环境可用。
- 每个能力至少有唯一 `name`、`description`、执行位置 `executor`、副作用标记 `mutating`、参数说明 `params_schema` 和可运行的 `argv_example`。使用 JSON Schema 表达参数类型及必填项；参数对应的 CLI 选项或位置要清楚，条件性写入采用保守标记并解释。
- 说明 JSON 是能力描述还是可直接提交的请求体；若只描述 CLI 参数，调用方仍须按命令行接口传参，不虚构 JSON 调用接口。需要单项查询、结果 schema 或动态后端能力时按实际支持单独说明，不假定所有工具都与 Unity CLI 相同。
- 静态能力文件须与实际入口版本一起维护；能力发现应可独立读取，避免为查看 schema 启动服务或触发联网下载。原生动态发现若依赖运行环境，应明确该前提与失败行为。

### 验收

- 检查入口的可执行权限、帮助和版本、JSON 可解析及字段与示例的一致性；测试空格路径、标准输入输出、错误退出码以及依赖缺失。若包装保留可联网或写入能力，按授权范围验证副作用和恢复行为。
- 对列出的每项常用能力至少验证代表性成功路径；写入或重构在临时副本验证预览、落盘及无关内容保持。对实际项目或文档的只读测试单独报告，不能把样本验收写成生产验收。
- 新增或升级能力时检查 schema、实际参数、版本和关联技能一致；未测试的格式、平台、后端及边界明确记录，不用 mock 结果代替真实接口验收。

## 维护检查

1. 核对任务范围、现有入口、Git 状态和其他窗口改动。
2. 按上述位置实现技能或 CLI，并维护对应账本、README 与相互链接。
3. 执行相关元数据、链接和实际行为验证；区分源码收录、用户级安装、工具依赖和运行验收。
4. 汇报入口、验证结果、已知限制和未完成事项。提交或发布按单独授权处理。
