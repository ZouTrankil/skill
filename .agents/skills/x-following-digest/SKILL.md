# X 关注动态简报

只以当前用户关注的人为动态来源，默认汇总运行截止时刻之前连续 24 小时的内容，中文输出。执行一次采集、分析和推送；调度由 Orca 管理，不在技能中创建定时器。

## 输入与执行状态

先读取本次指定的配置文件，未指定时读取 `~/.local/state/x-following-digest/config.json`。本次明确参数优先于配置；字段定义、首次配置和历史恢复见 [配置与运行检查](references/configuration.md)。默认展示时区为 Asia/Shanghai，内部时间使用 UTC。未指定主题时按实际内容归类，不自行限缩到财经或 AI。

本机状态默认放 `~/.local/state/x-following-digest/`，不放公共技能仓库。配置仅存账号标识、频道标识和凭据引用；token、cookie 留在现有密钥存储或已登录浏览器中。自动化缺少来源或目标配置时记录具体缺项并结束，不能猜频道、切换账号或转发到默认私聊。

区分三种请求：正式采集推送先检查来源及发送配置；明确预览只检查来源并记 `preview_only`；修复/配置技能先查历史证据、重新验证来源并保存已确认字段，缺少目标时询问具体缺项，不用发送测试消息代替配置验证。用户要求“配置缺失即结束”的执行任务不能自动转为预览或配置修复。试跑结束时记录哪些配置已保存、哪些还缺失，不能把预览成功报告为正式推送就绪。

冻结 `window_start`、`window_end`，使用半开区间 `[start,end)`；延迟执行以实际截止时刻为准，显式窗口则原样使用。重跑沿用原窗口与已生成的正文。不要将“最近一天”改成上一自然日。中断造成的更早缺口单独报告，不悄悄扩大窗口。

## 采集

先阅读 [接口与数据约定](references/access.md)，确定实际可用的访问方式；按 [采集、筛选与复核](references/collection.md) 使用单一来源会话、分页检查点和离线候选整理。优先复用已经验证的 Aside X 适配器，避免每轮重新探索接入方式。

1. 核对来源账号身份，分页取得其 **following** 名单，以稳定 user ID 组成白名单并记录获取时刻。不能用 followers、推荐账号、列表成员或曾经互动的人代替。
2. 通过只读 API 获取白名单用户的原创、带评论的引用及有实质内容的回复，翻页覆盖窗口。官方 API 可逐用户读取，也可用时间线发现候选后补齐；按作者 ID 再次过滤。关注者很多时逐批执行并保存游标，不以任意前 N 人替代全部范围。
3. 没有评论的转帖只记为“某关注用户转发”，不等于赞同。未关注作者的原文仅作明确标注的必要上下文，不列为独立观点来源。缺少转发事件时间时，不能仅凭原文日期判断它在本窗口被转发。
4. 保存 post ID、作者 ID/用户名、原文链接、发布时间、采集时间、正文、帖子类型、会话/引用关系和可用的媒体说明。保留长文展开后的正文；不能从标题、截图占位或视频封面编造观点。引用的旧帖可补上下文，但不计作本窗口新动态。
5. 按 post ID 去重，同一作者的连续线程合并，保留不同作者对同一事件的独立立场。商业广告、纯表情和无实质内容的寒暄计入过滤统计；有事实或观点的负面、少数意见不因不受欢迎而过滤。

采集结束记录关注人数、完成检查人数、有效帖子数、过滤数、失败账号、分页终点和最早覆盖时间。只有关注名单及每个来源的窗口覆盖都得到验证，才能标为完整；接口上限、限流、受保护内容不可读或游标异常必须标为部分覆盖。采集失败不等于“没有新动态”。遇到 401/403 停止受影响来源并说明授权问题；429 按服务端等待时间处理，最多重试两次，仍失败则保存进度。

## 分类、观点与冲突

先分批分析全部有效候选，再跨批次归并主题与对立主张，最后挑选代表帖补全文；不能先按长度或热度抽样再判断全天没有冲突。按当天实际主题组织，例如 AI/技术、产品/商业、市场/宏观、政策/社会、其他；不强凑空分类。每类回答“发生了什么、谁提出了什么观点、其理由是什么”，附作者和原帖链接。多条内容可以归并为一个事件，但保留有实质区别的意见。按证据和信息价值排序，互动量仅作背景。

将事实陈述、预测、价值判断、个人经历分开。作者声称的事实在核实前仍是其说法；事实核验可读官方公告、原始论文或数据，核验材料另列，不能借机把未关注账号扩成日报来源。受保护账号内容可在本地分析，但外发到频道前需要用户对该类内容的明确分享授权；未配置时仅报告省略数量。

对讨论同一对象、同一时期且前提可比较的立场检查冲突：

- 列出 A/B 的原意、作者和链接，指出相互不兼容的具体主张。
- 区分事实冲突、因果解释不同、预测不同、价值偏好不同；短期与长期、不同指标口径不强行算矛盾。
- 给出独立的 **AI 分析**：现有证据更支持哪一方、理由、关键假设、反证条件、尚缺什么信息；无法裁决时直接说明。
- 不能为了完成栏目编造对立。没有可比冲突时说明结论覆盖的是全部已采候选还是部分入选帖；只分析少量样本时不能宣称本窗口没有冲突。

AI 可以形成倾向，但不能把推断写成已证实事实，也不能靠投票数、作者声望或重复转发决定真假。

## 成果与 Telegram 推送

输出一份可独立阅读的中文简报：

1. 时间窗口和覆盖情况，以及 3–6 条主要信息（不足时按实有数量）。
2. 按主题展开的事件、观点、理由和原帖链接。
3. 单独列出的观点分歧及 AI 分析。
4. 值得继续观察的问题、采集缺口或未核实事实。

在状态目录按账号和窗口保存 `raw_timeline.jsonl`、`following.json`、分页检查点及候选整理结果；`posts.jsonl` 保存最终入选帖与正文复核状态，`coverage.json` 分别记录采集、分析和正文复核覆盖，`digest.md` 保存实际推送正文，`delivery.json` 保存发送回执。原始材料和摘要分开，支持离线重做分析；不保存认证头。重跑先检查相同账号、窗口、目标的记录，并取得单实例锁，避免两个 Orca 运行同时推送。

本次请求或既有自动化已明确要求向指定目标推送时，直接执行，不每次重新确认。仅要求预览/创建技能时保存草稿，不借验证技能发送消息。

- 优先使用可指定目标的既有 Telegram/Florence 通知工具；读取其实际技能并核对路由。指定 channel 时不能擅自使用通知工具的默认私人 chat_id，也不能把 bot 名称当 channel。
- 用户明确选择 Florence 路由及其私人目标时，将 `bot` 和 `chat_id` 显式保存并传入每次请求；称其为聊天目标，不声称是频道。只指定技能而仍要求 channel 时，不能据此采用技能的默认私聊。
- 若使用 Telegram Bot API，从密钥存储取得已有 bot token；用 `getChat` 验证目标为指定 channel，用 `getMe`、`getChatMember` 核对机器人及发帖权限。缺配置时保留草稿，报告缺项。
- 长文按主题分段，保留原帖链接和 `i/n` 编号。纯文本每段保守控制在 3500 个 UTF-16 代码单元内；使用 HTML/Markdown 时正确转义并计入平台长度规则，不截断 URL 或 Unicode 字符。
- 发送前记录该段正文摘要和 `sending` 状态。逐段保存返回的 chat ID、message ID 或中继通知 ID；成功回执到达后再标记已发送。中继 `pending` 只表示排队，不能报送达。
- 超时或断连属于结果不明；若没有可核对的送达记录，停止该次推送并保留 `unknown`，不能自动重发。恢复时仅续发明确未发送的段，不重新生成整篇后从头推送。

结束时报告简报位置、来源覆盖程度和发送结果。部分覆盖允许发送，但标题必须标明“部分覆盖”；来源整体不可用时不生成假日报，只记录错误。成功采集且确实无新内容时可向已配置目标发送简短的“本窗口无有效新动态”。

## Orca 调用

自动化提示词指定本技能路径、配置路径及状态目录，要求执行完整的一次工作流；账号、访问方式和目标以本机配置为准，不在提示词另存一份易过期的副本。调度时间、时区和启用状态保存在 Orca；修改它们时使用 `orca-cli` 技能和实际运行版本的 automations 指南。只有获准设置调度时才创建或修改任务；配置与接入未就绪时保持禁用，不因修复技能自行启用。每次运行重新验证账号、关注名单和窗口，不复用上一轮的“已关注”推断。
