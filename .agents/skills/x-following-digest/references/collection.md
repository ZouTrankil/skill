# 采集、筛选与复核

在开始采集或恢复中断任务时读取。原则是原始数据只采一次，筛选与摘要可以离线重跑；缩短无效操作，不能靠缩小作者或内容范围提速。

## 一次来源会话，分阶段交付

使用一个 Aside agent 会话负责账号、名单和采集。后续通过同一 session 继续，避免多个 agent 同时切换同一页面。调用方负责离线筛选、主题归并和最终分析，不反复让浏览器 agent 重做整份报告。

1. 读取当前适配器文档，`getMe` 成功后复用结果。首次时间线探测返回的数据及 cursor 纳入正式采集，不能丢弃后重新读第一页。
2. 本轮重新核对 Following 名单。逐次加载后合并新账号，滚动是触发加载，不是固定滚动 N 次就算完成。记录末端状态与名单数量；数字相同只作交叉检查，不能代替名单身份核验。
3. 名单缓存保存 ID、handle、核验时间和来源。本轮名单与旧名单按 ID 比较，发现更名、增减或 ID 冲突时更新。可用本轮帖子返回的作者 ID 辅助解析当前 handle，对无法确定的作者才额外查 `getUser`；不能把旧名单当当天白名单。
4. 每页落盘后推进检查点，保存输入/输出 cursor、页号、原始记录数、新增唯一 ID 数、窗口内新增数和时间范围。先保存数据再更新 cursor；中断从已落盘的最后 cursor 继续。部分补全失败不重采成功页。
5. 日志只打印页级统计、异常和产物路径，避免在工具输出中反复倾倒整条时间线。落盘保持原始记录，摘要阶段读取过滤后的数据。

## 分页终点与完整度

时间线可能包含广告、旧原文转发和乱序内容。不得用“遇到任意一条旧帖”或页面最后一条的日期结束采集，也不得把重复 cursor 当成成功遍历。

- 无 nextCursor：记录接口末端，仍检查产品上限及窗口是否覆盖。
- cursor 重复、连续请求没有新 ID 或持续限流：保存异常与检查点，停止该来源并标记部分覆盖。
- 快速预览可在连续两页没有新增名单内窗口候选、且正常原创/回复已经越过下界时停止候选发现。记录启发式终点；不能由此声称全量。
- 正式完整采集需要对所有关注账号检查窗口，按作者分页补齐，并记录该端点是否包含回复/引用。时间线中没有出现的作者不能判定“当天未发帖”。端点不支持的类型明确作为缺口；时间预算不足时保存队列后返回部分报告。

不要使用预览的固定页数、时长或帖子数作为正式任务的完成条件。独立账号请求可以在接口允许时小批并发，初始并发 2；游标链及共享网页操作串行。根据实际限流响应降并发，不用无限重试。

## 离线准备候选

复用 [prepare_candidates.py](../scripts/prepare_candidates.py)：只使用 Python 标准库，不访问网络。输入是本轮 `following.json`（`accounts` 中包含 `handle`、可选 `id` 及关注证据），以及每行 `{ "tweet": <Aside XTweet> }` 的 `raw_timeline.jsonl`。

```sh
python3 <技能目录>/scripts/prepare_candidates.py \
  --raw <本轮目录>/raw_timeline.jsonl \
  --following <本轮目录>/following.json \
  --start <带时区的窗口起点> --end <带时区的窗口终点> \
  --output-dir <本轮目录下尚不存在的整理目录>
```

输出 `candidates.jsonl`、待核实转发时间的 `reposts.jsonl`、无效行 `rejected.jsonl` 和统计 `preparation.json`。退出码 2 表示存在无效行，不能忽略；输入格式或目录冲突直接报错。脚本不判定全文、广告或完整覆盖。ID 保持字符串，按 `[start,end)` 过滤；JSONL 按 LF 解析，不能用 `splitlines()` 拆开正文内的 Unicode 行分隔字符。

## 先分析全部候选，再补全文

对全部 `candidates.jsonl` 分批提取事件、主张、依据、时间尺度和帖子类型，为每条记录保留去向：纳入主题、上下文、无实质内容、广告或待补全文。不能按 70–215 字等长度条件、互动量或是否方便读取来预先排除内容。帖子中的营销和观点混合时保留有独立信息价值的主张并注明利益背景。

先跨批次合并事件和相反主张，再挑代表帖进入最终简报。发现冲突线索时回看双方原文；不能先抽取少数帖子再宣称整个窗口没有分歧。核对“候选总数 = 已处理各类记录 + 尚未分析记录”，未分析部分在覆盖报告中披露。

只有对摘要重要、明显截断、跨帖回复、引用归属不明或证据有冲突的内容才补充详情。先尝试 `getTweet` / `getTweetThread`，返回仍截断则去网页；已确认完整的短帖无需每条再打开网页。保存字段级核验状态，区分 `api_only`、`web_confirmed`、`truncated`、`unavailable`，不把前者冒充后者。

网页核对必须找到 permalink 的 status ID 与目标 ID 相同的 article，并核对作者、时间；不能使用 `article.first()`，回复页首条经常是父帖。展开长文后再读取目标 article 的正文；找不到目标就保留未核验状态，不把父帖正文写回目标回复。引用内容与当前作者自己的评论分别保存。

## 输出前检查

- 候选、入选帖子都满足本轮关注证据和窗口条件；引用背景与转发时间不明项单独标注。
- 原文、URL 中的作者与 post ID 一致；统计能从本地文件重算。
- `coverage.json` 分开写采集覆盖、候选分析覆盖和正文复核覆盖，不能只用一个“完成”标签。
- 同一窗口可重做分析，不必重新采集；新增抓取应追加来源证据和新时间，不能覆盖先前冻结的事实。

## 已观察到的问题（2026-10-29）

一次预览的 1,012 条原始记录中，171 条来自未关注作者；名单内窗口候选去重后 596 条，其中 116 条标为转发、480 条为非转发。第一页混有 15 条旧帖，随后仍有 503 条新增有效候选。70–215 字筛选只留下 208 条非转发候选，遗漏其余 272 条。末两页未带来新的名单内窗口候选，但这不证明每个作者的所有回复均已覆盖。实际回复页还出现过首条 article 是父帖的问题。

这些是流程修正依据，不是固定页数、数据量或耗时承诺。API 请求次数、页面打开次数及运行时长应在下一次真实采集中测量后再比较。
