# 代码规范与评审

帮助代码满足实际需求、保持清晰，并识别可证实的正确性和维护风险。遵循项目现有技术栈与规范，不把个人风格或某种架构偏好作为合并门槛。默认中文说明，代码标识符沿用项目习惯。

## 确定工作模式和范围

- **编码/重构**：在用户指定范围内实施变更，用下述标准自查并验证；不顺手重构无关模块。
- **评审**：默认只读，提供发现和建议补丁；用户明确要求修复时才写入。不要因调用本 Skill 自动提交、推送或发布评审评论。
- 尊重指定的文件、提交或 PR 范围。未指定时，有本地改动则审查 staged、unstaged 和相关未跟踪源码，分别确认差异；排除无关产物。不把 `git diff` 当成完整工作区状态。
- 工作区干净且未指定范围时，从 PR 元数据或明确的分支约定确认目标分支，以 merge-base 为比较起点；无法可靠确定时询问范围，不猜测 `main` 或默认把最后一次提交当成目标。
- 先确认仓库、分支和状态，读取适用的 AGENTS.md、项目规则、相关 README、构建和 lint 配置。按作用域采用 CLAUDE.md、Cursor Rules 等规则，不把所有目录的规则混用。

## 编码标准

优先复用已有业务能力、错误模型和公共接口；在动手前找到真实入口和调用方。

- **职责与复杂度**：按业务职责组织代码，用当前需求证明抽象的必要性。避免未使用的扩展点、重复实现和只有转发作用的新层；不以函数行数或层数作为机械判定标准。
- **契约与边界**：明确输入、返回值、状态变化及失败语义。区分空值、零值和缺失值；检查单位、时区、精度与边界。公共接口变化同步检查调用方、序列化和兼容策略。
- **错误与资源**：保留错误上下文，避免吞错或以成功值掩盖失败。保证异常和取消路径释放资源。涉及网络与重试时明确超时、重试边界及重复执行的影响。
- **并发与数据一致性**：按实际并发模型检查共享状态、锁顺序、事务边界和幂等；不要只凭存在锁或事务就认定安全。
- **安全与性能**：在相关边界检查授权、输入进入 SQL/命令/路径的方式、敏感信息泄露，以及无界查询、队列、内存和重复 I/O。以真实调用与数据规模说明影响，不凭想象要求全项目加固或优化。
- **语言惯用法**：遵守仓库支持的语言与依赖版本，采用已有惯用写法；不为“现代化”引入不兼容语法、依赖升级或全局风格迁移。
- **可测试性**：使关键业务行为能通过已有测试入口验证。按风险选择单测、集成或端到端测试，不强制所有函数可 Mock，不为测试额外引入无实际需要的抽象。

## 评审流程

1. **理解意图**：结合需求、差异和真实调用链确认变更想改变什么。简要记录审查基线及覆盖范围。
2. **分离机械检查**：格式、语法和确定性的静态规则交给项目现有 formatter、linter、类型检查。评审时使用检查模式，不自动格式化或修复。相关失败简述即可，不逐条重复工具输出。
3. **追踪影响**：以 diff 为入口，读取必要的完整函数、调用方、配置和测试，检查上述编码标准。重点报告本次引入或触发的问题；既有问题不归咎于本次变更。用户要求全模块审计时按指定范围扩大检查。
4. **验证候选问题**：每条发现必须能说明触发条件、代码路径和实际影响。核对上游校验、框架保证、已有测试与项目契约，排除误报。同一根因合并报告，不为凑数量制造问题。
5. **给出修复**：上下文充分时提供最小 unified diff 或 Before / After，使用当前代码中的真实标识符。无法可靠生成补丁时，给出具体修改位置、约束和验证方法，明确缺失信息；不编造 API、行号或可直接运行的承诺。
6. **选择验证**：优先执行与行为相关的已有检查，满足项目强制门禁。测试必须有能力暴露缺陷，覆盖相关失败路径；简单低风险改动不为了数量新增测试。未经执行的建议补丁标明未验证。需要真实服务、凭据或有外部副作用的验证时，遵循任务授权并说明未覆盖范围。

## 问题等级

优先采用项目既有等级；没有约定时使用下表。严重程度与证据充分程度分开：不确定的问题不能靠降级包装成已确认缺陷。

| 等级 | 判定依据 | 处理建议 |
| --- | --- | --- |
| Blocker / 阻断 | 有证据的关键流程不可用、严重安全漏洞、不可恢复数据损坏等 | 合并前修复 |
| Major / 重要 | 在明确条件下产生错误结果、兼容性破坏、资源泄漏或显著性能退化 | 原则上合并前修复；说明影响范围 |
| Minor / 建议 | 有具体维护收益、但不影响当前正确性的改进 | 不单独阻塞合并 |

纯个人偏好不列为缺陷。缺少测试时说明哪项重要行为没有保护，不把“未新增单测”本身视为阻断。证据不足的高风险疑点单列“待确认”，写明缺什么及如何确认。

## 交付方式

遵守用户或评审平台要求的输出格式；没有要求时：

- **评审**：先列发现，按严重程度排序。每条包括 `[等级] 具体问题 — 文件:行号`、触发条件与影响、代码证据、最小修复及验证方法。行号对应当前审查版本，定位尽量短；说明依赖的其他位置。建议补丁保持必要长度。
- 随后简述覆盖范围、已执行的验证和未验证项。复杂改动可补充简短改动概述；只有用户需要时才给逐文件 Walkthrough，不让总结淹没问题。
- 没有发现时写“在本次审查范围内未发现可确认的问题”，同时说明检查限制；不把静态审阅等同于运行验收通过。
- **实施/修复**：说明实际改动、验证结果和仍未解决的问题，区分已实现、已验证与建议。任务期间目标文件被其他人修改时，重新读取并合并意图，不覆盖已有改动。
