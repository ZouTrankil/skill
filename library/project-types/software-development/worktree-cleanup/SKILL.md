# Worktree 回收

先确认任务结束和成果安全，再通过原管理工具移除 worktree。长期未修改、分支已推送或工作区干净，都不能单独证明可回收。默认保留分支。

## 范围与共用清单

- 优先使用本次指定的仓库/工作根目录或清单；否则使用 `SYNC_REPOS_FILE`，再否则查找当前可用 `local-repo-sync` 技能源码旁的 `repos.tsv`。通过技能列表定位或解析本技能真实路径后查找同级 `local-repo-sync`；不可依赖当前工作目录。缺少来源时询问位置，不扫描整个磁盘。
- 与 `repo-artifact-cleanup` 共用该清单，不另建仓库名单。TSV 每行是仓库绝对路径、remote、基线分支及可选说明；忽略空行和以 `#` 开头的行。按制表符解析并检查缺字段，路径不按空格切分。读取名单不意味着运行同步、提交或 rebase。
- 对明确的工作根目录仅在其范围内查找仓库标记，排除依赖、生成物且不跟随目录符号链接；以 Git 实际登记核实，不能根据目录名判断。按规范化 Git common directory 去重仓库，再读取 `git worktree list --porcelain`；涉及特殊路径时使用当前 Git 支持的无歧义输出方式。
- 仓库登记可以用于发现外部 worktree，但删除范围仍受用户指定根目录或已授权路径约束；范围外项只报告。默认保护主工作树、当前会话所在工作树及其上级目录，避免清理自身工作目录。
- 两种清理技能可共用用户指定的策略，按仓库记录允许处理的 worktree 范围、保护项、任务结束证据来源、保留期、允许动作和记录位置。没有明确执行范围与授权时只检查，不自行设置到期天数。

## 回收判断

1. 识别 Git 之外的管理状态。Orca 管理的 worktree 使用当前可用 `orca-cli` 技能及其正式入口；其他管理器沿用其接口。管理器不可用或无法确认归属时保留，不直接用 Git 或文件删除绕过管理器。
2. 查任务完成记录、用户明确的完成说明或管理器任务状态，并检查活跃会话、终端、工作目录占用与服务进程。进程检查不完整或状态不明时列为待判断，不终止未知进程。`locked` 项保留。
3. 分别检查 staged、unstaged、未跟踪文件、被忽略文件、嵌套仓库与子模块状态，以及进行中的 merge/rebase 等操作。任何未保存成果或用途不明产物都阻止回收；干净的普通 `git status` 不能代替忽略文件检查。
4. 记录 worktree 的 HEAD、分支、明确的目标基线及提交关系。使用可信的任务基线，不能猜 `main`。核对独有提交是否已纳入目标历史、是否有可靠保存位置，以及任务是否确已结束。缓存的远端引用不能冒充已核验远端状态；需要实时证据且不能获得时保留。
5. squash/rebase 合并造成的非祖先关系需结合实际合并记录和内容判断；不能因为单次祖先检查失败就认定成果丢失，也不能仅凭同名分支或已推送判为可删。独有提交用途不明时保留；detached HEAD 的独有提交未被可靠引用保护时禁止回收。
6. 已忽略的日志、脚本、数据或截图仍可能是唯一成果。必要时按 `repo-artifact-cleanup` 的规则评估并在授权范围内保留，验证原路径、保存位置和内容摘要；不能仅删除忽略项来让回收命令通过，也不把另一技能已执行作为事实。

输出每个 worktree 的路径、分支/HEAD、任务证据、占用、改动/产物、提交保护状态及建议。请求检查时到此为止；已有明确执行授权时继续处理符合条件的项，不重复索要相同授权。

## 执行与复核

- 两种清理技能共用仓库锁：以规范化的 Git common directory 绝对路径的 SHA-256 为键，在用户状态目录 `repo-cleanup/locks/` 中原子创建锁目录。macOS/Linux 使用 `${XDG_STATE_HOME:-$HOME/.local/state}`，Windows 使用 `%LOCALAPPDATA%`。记录运行 ID 和所有者；已有锁则跳过，不自动移除未知锁，只释放本次获得的锁。
- 先完成必要成果保存，再获取锁并重新检查登记信息、HEAD、全部文件状态、保护规则及占用情况；若与报告不一致，重新判断。与产物技能衔接时不要在持有同一锁的情况下递归获取锁。此锁不能阻止其他开发进程，无法排除并发使用时跳过。
- 保存操作记录：仓库、原路径、HEAD、分支、任务结束证据、成果保存位置及摘要、使用的管理器、允许动作和 `planned` 状态。记录放在 worktree 外的用户状态目录 `repo-cleanup/worktree-cleanup/`，按运行 ID 区分；记录写入失败时不移除。
- 普通 Git worktree 使用明确路径的 `git worktree remove`，不用 `--force`；托管 worktree 使用原管理器移除。先核对接口是否连带删分支或其他资源，有超出授权范围的副作用时停止该项。命令拒绝时检查原因，不能改用 `rm -rf` 绕过。
- 不自动 commit、stash、push、reset、删分支或处理其他人的锁。需要额外保存提交或产物时先完成具体方案，并按该动作已有授权执行；缺少授权则保留并报告。
- 移除后核对磁盘路径、Git worktree 登记、管理器状态及原分支仍存在，更新记录为成功或失败。超时或中断先检查真实状态，不盲目重试。
- 失效登记单独报告。仅在明确授权且确认路径永久失效后处理；暂时离线的磁盘、网络目录及锁定项保留。批量 `prune` 可能影响其他登记，必须先预览完整影响范围，不把它当成单个 worktree 删除命令。
- 单仓库失败不阻塞其他仓库。按已配置期限轮转完成记录，未解决的失败和仍有恢复依赖的记录保留。

## 恢复与定期运行

移除 worktree 不等于具备完整回滚能力。保留的分支/提交可用于重建源码工作树；未跟踪或忽略内容只能从已验证的保存副本恢复。托管工作树通过原管理器重建，不承诺恢复终端或会话。恢复前确认原路径可用且不会覆盖现有内容。

报告已回收、保留、待判断和失败项，注明分支保护、成果位置、记录位置及恢复限制。不要把候选数量当成已回收数量。

本技能定义一次由代理执行的流程，不附带无人值守回收程序。调度器负责周期触发，只有用户要求时才配置；定期执行仍需可靠任务证据和授权范围，不因无人应答而强制回收。
